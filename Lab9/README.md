# Лабораторна робота №9 — Рефакторинг та SOLID (C++), варіант 12

Структура: `Library/` (обов'язкове завдання) і `LeaderBoard/` (Kata №3, варіант 12).
Збірка: `cmake -B build -S . -DCMAKE_TOOLCHAIN_FILE=<vcpkg>/scripts/buildsystems/vcpkg.cmake && cmake --build build && ctest --test-dir build`

## 1. Система управління бібліотекою

### Аналіз початкового коду
- `Book` об'єднує дані, виведення, збереження в БД і email-сповіщення → 4 причини для зміни.
- `Library` зберігає колекцію, але ще й сама ініціює збереження/сповіщення через методи `Book`.
- Публічні поля `title`, `author` — слабка інкапсуляція.
- Початковий код навіть не компілюється: `addBook(const Book&)` та `displayBooks()` викликають неконстантні методи `Book` на `const`-об'єктах.

| Принцип | Висновок |
|---|---|
| SRP | **Порушено**: `Book` відповідає за дані, друк, БД, email |
| OCP | **Порушено**: щоб додати SMS чи інше сховище, треба змінювати `Book`/`Library` |
| LSP | Не порушується: успадкування в коді немає |
| ISP | Не порушується: великих інтерфейсів немає. Після рефакторингу інтерфейси вузькі (по одному методу) |
| DIP | **Порушено**: високорівнева логіка залежить від конкретних дій «збереження в БД» та «email» |

### Результат
`Book` (лише дані, приватні поля) · `IBookRepository` + `DatabaseBookRepository` · `IBookNotifier` + `EmailNotifier` · `Library(IBookRepository&, IBookNotifier&)` (DI через конструктор).
Заміна сховища чи сповіщень не потребує змін `Library` — доведено тестами з fake-реалізаціями. Вивід програми збігається з очікуваним початковим.

```
Library --> IBookRepository <|-- DatabaseBookRepository
        --> IBookNotifier   <|-- EmailNotifier
        o-- Book
```

## 2. Kata №3 — LeaderBoard (Racing-Car-Katas / Cpp/LeaderBoard)

`LeaderBoard/legacy/` — початковий код **дослівно** з репозиторію кату; `LeaderBoard/include`, `source` — результат рефакторингу.

### Виявлені проблеми початкового коду
| Проблема | Де | Принцип / smell |
|---|---|---|
| `Race` і рахує бали, і формує імена учасників | `Race` | SRP |
| `typeid(driver) == typeid(SelfDrivingCar)` + `static_cast` | `Race::Race` | OCP, Complex Conditional, Tight Coupling |
| `SelfDrivingCar : Driver` передає версію алгоритму як «ім'я» водія | `SelfDrivingCar` | LSP |
| **Slicing**: `std::list<Driver>` зберігає об'єкти за значенням, тож `SelfDrivingCar` обрізається до `Driver`; перевірка `typeid` ніколи не спрацьовує, і в рейтингу авто називається `"1.2"`, а не `"Self Driving Car - ACME (1.2)"` | `Race`, `Leaderboard` | LSP, дефект |
| `POINTS[position]` для 4-го і далі учасника — вихід за межі масиву (UB) | `Race::getPoints` | дефект |
| Таблиця балів `{25,18,15}` зашита в `Race` | `Race` | OCP, DIP |
| Некоректна константність, копіювання (`getResults()` повертає список за значенням, `Driver` передається за значенням) | `Race`, `Leaderboard` | Code smell |
| `Leaderboard` неможливо протестувати без реальних `Driver`/`SelfDrivingCar` | `Leaderboard` | Tight Coupling, тестованість |

### Кроки рефакторингу
1. **Тести «до»** (`CharacterizationTests.cpp` + `LegacyQuirkTests.cpp`) на оригінальному коді. Тест `SelfDrivingCarIsSliced...` фіксує дефект slicing.
2. Введено `IParticipant::displayName()`. `Driver` і `SelfDrivingCar` реалізують його незалежно; `SelfDrivingCar` більше не успадковує `Driver` (LSP), `typeid`/`static_cast` зникли (OCP).
3. `Race` зберігає учасників як `shared_ptr<const IParticipant>`, тож slicing неможливий. Старий конструктор `Race(name, std::list<Driver>)` залишено для сумісності.
4. Бали винесено в `IScoringSystem` (`ClassicScoringSystem` = 25/18/15); `Leaderboard` отримує її через конструктор (DIP, OCP). Вихід за межі масиву замінено на 0 балів.
5. Методи зроблено `const`, додано getter-и.
6. **Тести «після»**: той самий `CharacterizationTests.cpp` скомпільовано проти нового коду, усі проходять. Сумісність: `Leaderboard(races)`, `driverResults()`, `driverRankings()` працюють як раніше.

### Індивідуальне розширення
Додатковий критерій при однаковій кількості балів — **кількість перемог** (потім ім'я), метод `driverWins()`, плюс нова система нарахування `ExtendedScoringSystem` (топ-10). Реалізовано додаванням класів і одного методу, без зміни інших класів.

### Зміни, що ламають сумісність (свідомі)
- `SelfDrivingCar` більше не є `Driver`: передати його в `std::list<Driver>` не вийде (раніше це мовчки викликало slicing).
- `Race::getResults()` повертає `std::list<std::shared_ptr<const IParticipant>>`.
- Для 4+ учасників класична система дає 0 балів (раніше UB).
- Порядок при рівності балів: спершу за перемогами, потім за ім'ям (раніше лише за ім'ям). Якщо перемог порівну, результат збігається з оригіналом.

## 4. Використання інструментів штучного інтелекту

**Інструмент:** Claude (Anthropic).

**Мета використання:** консультаційна підтримка — аналіз структури коду та порушень SOLID, обговорення архітектури, підготовка початкового варіанта рефакторингу й тестів, пошук помилок.

**Що враховано:**
- поділ `Book` на дані, сховище (`IBookRepository`) і сповіщення (`IBookNotifier`) з передаванням залежностей через конструктор;
- у LeaderBoard — абстракція `IParticipant`, відмова від успадкування `SelfDrivingCar` від `Driver`, винесення нарахування балів у `IScoringSystem`;
- підхід «спочатку тести на старому коді, потім рефакторинг, потім ті самі тести на новому»;
- підказка, що початковий код бібліотеки з методички не компілюється (`const Book&` викликає неконстантні методи);
- виявлення дефектів оригіналу: slicing `SelfDrivingCar` у `std::list<Driver>` і вихід за межі масиву `POINTS` для 4-го учасника.

**Що відхилено або виправлено:**
- перша версія папки `legacy/` була відтворена ШІ за загальним описом, а не з реального репозиторію; вона була повністю замінена оригінальним кодом `Racing-Car-Katas/Cpp/LeaderBoard`, а рефакторинг перероблено під його справжній API;
- твердження ШІ, що порядок при рівності балів у оригіналі не визначений, виявилось хибним: сортування стабільне, порядок алфавітний; це виправлено в аналізі;
- припущення ШІ, що завдання Kata визначається номером варіанта, не було підтверджене методичкою, тому на нього не покладалась;
- згенеровані ШІ тести й код не приймались без перевірки: усе зібрано та запущено локально (vcpkg + GoogleTest, `ctest`).

**Висновок щодо ШІ:** запропонований код використано як відправну точку; архітектурні рішення, призначення класів та інтерфейсів, а також результати тестування перевірено й можуть бути пояснені під час захисту.

## 5. Висновки

У роботі виконано рефакторинг двох програм із застосуванням принципів SOLID.

У системі управління бібліотекою клас `Book`, який об'єднував дані, друк, збереження в БД та email-сповіщення, розділено на окремі компоненти. `Library` залежить від абстракцій `IBookRepository` та `IBookNotifier`, а не від конкретних реалізацій, тому заміна сховища чи способу сповіщення не потребує змін її коду. Дані `Book` інкапсульовано. Принципи LSP та ISP у початковому коді безпосередньо не порушувались, оскільки там немає ні успадкування, ні великих інтерфейсів.

У Kata LeaderBoard виявлено порушення SRP (Race одночасно рахує бали й формує імена), OCP (перевірка типу через `typeid`), LSP (SelfDrivingCar успадковує Driver із підміною імені), DIP (таблиця балів зашита в клас), а також реальні дефекти: slicing, через який самокерований автомобіль втрачає своє ім'я в рейтингу, та вихід за межі масиву для четвертого учасника. Після рефакторингу ці проблеми усунуто за допомогою інтерфейсів `IParticipant` та `IScoringSystem`, а публічний інтерфейс `Leaderboard` залишився сумісним, що підтверджено тими самими тестами до й після змін.

Індивідуальне розширення — додатковий критерій рейтингу (кількість перемог при рівності балів) та альтернативна система нарахування балів — реалізовано додаванням нового коду без змін наявних класів, що демонструє дотримання принципу відкритості/закритості.

Рефакторинг підвищив тестованість (компоненти перевіряються незалежно, зокрема з підміною залежностей), підтримуваність (кожен клас має одну причину для зміни) і розширюваність (нові способи нарахування балів чи сповіщення додаються новими класами). Практично закріплено прийом роботи з успадкованим кодом: спершу характеризаційні тести, потім невеликі кроки рефакторингу з перевіркою поведінки.
