## 1. Система управління бібліотекою

### Аналіз початкового коду
- `Book` об'єднує дані, виведення, збереження в БД і email-сповіщення → 4 причини для зміни.
- `Library` зберігає колекцію, але ще й сама ініціює збереження/сповіщення через методи `Book`.
- Публічні поля `title`, `author` — слабка інкапсуляція.
- Початковий код навіть не компілюється: `addBook(const Book&)` та `displayBooks()` викликають неконстантні методи `Book` на `const`-об'єктах.

| Принцип | Висновок |
|---|---|
| SRP | **Порушено**: `Book` відповідає за дані, друк, БД, email |
| OCP | **Порушено**: щоб додати SMS чи інше сховище, треба змінювати `Book`/`Library` |
| LSP | Не порушується: успадкування в коді немає |
| ISP | Не порушується: великих інтерфейсів немає. Після рефакторингу інтерфейси вузькі (по одному методу) |
| DIP | **Порушено**: високорівнева логіка залежить від конкретних дій «збереження в БД» та «email» |

### Результат
`Book` (лише дані, приватні поля) · `IBookRepository` + `DatabaseBookRepository` · `IBookNotifier` + `EmailNotifier` · `Library(IBookRepository&, IBookNotifier&)` (DI через конструктор).
Заміна сховища чи сповіщень не потребує змін `Library` — доведено тестами з fake-реалізаціями. Вивід програми збігається з очікуваним початковим.

```
Library --> IBookRepository <|-- DatabaseBookRepository
        --> IBookNotifier   <|-- EmailNotifier
        o-- Book
```

## 2. Kata №3 — LeaderBoard

### Початкові проблеми
- `Race` рахує бали **і** формує імена учасників (SRP); має `dynamic_cast<SelfDrivingCar*>` — тип-залежна логіка (OCP, Tight Coupling).
- `SelfDrivingCar : Driver` передає порожнє ім'я — «фальшиве» успадкування (LSP).
- Таблиця балів `{25,18,15}` зашита в `Race` (OCP/DIP); публічні поля (інкапсуляція).
- `LeaderBoard` не можна протестувати без реальних `Driver`/`SelfDrivingCar`/`Race`.

### Кроки рефакторингу
1. Характеризаційні тести (`CharacterizationTests.cpp`) на початковому коді — **усі проходять**.
2. Введено `IParticipant::displayName()`; `Driver` і `SelfDrivingCar` реалізують його незалежно (немає успадкування між ними → LSP, `dynamic_cast` зник).
3. Бали винесено в стратегію `IScoringSystem` (`ClassicScoringSystem`) → `LeaderBoard` отримує її через конструктор (DIP, OCP).
4. `Race` став простим носієм результату; приватні поля + getter-и.
5. Той самий файл характеризаційних тестів скомпільовано проти нового коду — **усі проходять** (сумісність `LeaderBoard(races)`, `driverPoints()`, `driverRankings()` збережена).

### Індивідуальне розширення
Додатковий критерій при однаковій кількості балів: **кількість перемог** (потім ім'я для детермінованості) + нова система балів `ExtendedScoringSystem` (топ-10). Реалізовано без змін наявних класів: новий метод `driverWins()` і новий клас стратегії.

> Примітка: у початковому коді порядок при рівності балів не був визначений; тепер він детермінований. Для 4+ учасників класична система дає 0 балів.
